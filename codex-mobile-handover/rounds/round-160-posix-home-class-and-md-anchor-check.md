## 二、① POSIX 家目录类（收 round-159 §六.7）

**现象/需求：** round-159 §六.7 记「新增的『盘符家目录骨架』类是按 §5.4 正文来的；但 **POSIX 家目录骨架**仍未建类，其在仓内 md 的命中数**未量**」。

**根因：** 已有 9 类里能标识家目录的只有**盘符**形态（盘符 + `Users`）；macOS 的 `Users` 家目录与 Linux 的 `home` 家目录**同样标识这台机器**（换机 / 换平台必然不同），却一条都没拦。

**修复：** 补两类（仍是「按类不按清单」）——
- `POSIX 家目录-真实用户名`：家目录后跟真实用户名；
- `POSIX 家目录骨架`：家目录后跟 `<` 占位符。

两类都沿用已有的**前置否定环视**（`(?<![A-Za-z0-9._:+\/-])`），所以 `https://host/...` 这类 URL 路径、以及「盘符 + `Users`」形态都不会被误判成本类。

**先量后修，但「量」的口径要和闸门一致（本轮第一个教训）：** 先用一段离线侦察脚本在仓内 md 上跑候选类，只看到 1 处夹具路径；**闸门实跑却出 13 处**。差别在于侦察脚本**先剥了代码**（复用 round-159 链接闸门的 `stripCode` 思路），而脱敏闸门是**按行扫原文** —— 于是**代码块 / 行内代码里的路径**也进了闸门。⇒ 「先量后修」这步**必须用与闸门同一口径**，否则会低估修复面（差 1 处 vs 13 处）。

**13 处的分类处理：**

| 类别 | 处数 | 文件 | 处理 |
| --- | --- | --- | --- |
| 指向某 Linux 测试机的**真实**家目录（Oracle A1 ARM64 Ubuntu 实例 —— 该 `tests/` 文档明写「A1 server: Ubuntu ARM64」） | 6 | `tests/chat-composer-rendering/`（2 个）、`tests/thread-loading-state/`（1 个） | 家目录真实用户名 → `<用户主目录>` |
| 描述 macOS 家目录形态（「does not resolve … as local files」） | 1 | `.agents/skills/codex-app-parity/SKILL.md` | 改写为 `absolute macOS home-directory paths (under /Users)` |
| round-159 文档 / 台账里「该骨架仍未建类」的**自指** | 4 | `rounds/round-159-*.md`、`sections/commit-history.md` | 改写为**抽象描述**（`/home` 与 `/Users` 下的用户名目录） |
| **夹具**路径（链接渲染示例，家目录下跟**保留示例名**） | 2 | `tests/chat-composer-rendering/...link...` | **登记例外**（任一机器上都不存在；用户名是保留示例名，不标识真实用户） |

**为什么「真实家目录」必须改、而夹具可以例外：** 前者的用户名是**真的**，路径还指向**另一台机器的另一个项目**的源码文件 —— 正是 §5.4 要拦的「能标识本机 / 本用户」；后者用的是 `example` 这类**保留示例名**，不标识任何真实用户，才归到例外。

**验证：** `node scripts/check-handover-desensitization.cjs` ⇒ **违规 0 处 / 例外 9 处（登记例外 6 条），退 0**（扫描 546 个 md，**11 类**）。

## 三、② 链接闸门加锚点校验（收 round-159 §六.8）

**现象/需求：** round-159 §六.8 记「链接闸门只校验存在性：`x.md#fragment` 只检查 `x.md` 存在，`#fragment` 是否指向真实标题**未校验**」。

**方法：** 给 `scripts/check-md-links.cjs` 加锚点校验 ——
1. 先给每个 md 建**标题索引**（`#{1,6}` 行 ⇒ 近似 github-slugger 的 slug）；
2. 链接带 `#` 时，除校验路径部分存在，还校验 `#frag` 命中目标文档的某个 slug；**同文件锚点**（`#frag`）一并校验；
3. **两个有意不判**：`#L<n>` / `#L<n>-L<m>`（GitHub 给**代码文件**生成的行号锚点，不是标题）、**目标非 md**（`.ts` / `.png` 的锚点不是标题锚点）。

**为什么必须加这两个口子：** 侦察里 8 条跨文件锚点**7 条是 `#L600` 这类行号锚点**（指向 `src/**/*.ts`）；不看「目标是不是 md」就会 **7/8 误报** —— 与 round-159「不剥代码 ⇒ 19 条误报」是同一类问题：**误报比漏报更伤闸门**（它会训练人忽略输出）。

**自己踩的坑（第一版就错）：** 标题索引一开始复用了 `stripCode`（它连**行内代码**一起剥），于是标题 `## 巨型 \`.vue\` 第二轮组件化评估（2026-08-28）` 里的 `.vue` 被抹掉、slug 少了 `vue`，导致**修对了链接却仍报失效**。⇒ 标题索引**只能剥围栏块**，标题内的行内代码**只去反引号、保留文本**（GitHub 的 slug 正是保留文本）。

**结果：** 校验 **2553 条相对链接 + 2 条锚点**；修掉 **1 条真失效锚点** —— `rounds/round-62-*.md` 指向 `sections/domain-modularization-plan.md` 的锚点**少了标题里的日期后缀**（标题是「巨型 `.vue` 第二轮组件化评估（2026-08-28）」，锚点却只写到「…组件化评估」）⇒ 补全为完整 slug。终态 **失效链接 0 / 失效锚点 0**。

## 六、诚实边界

1. **零产品代码改动** ⇒ 本轮**未跑** `vue-tsc` / 全量单测 / `vite build`（基线仍以 round-157 的 **998 例 / 87 文件**为准）。
2. **锚点校验用「近似 github-slugger」**：去 HTML、小写、去标点、空格转连字符、保留 Unicode 字母数字。**个别标题**（含内联 HTML 锚点、脚注、emoji、或 GitHub 另加的去重后缀 `-1`）可能与 GitHub 实际 slug 有偏差 ⇒ 那一类链**可能漏报**（一般不会误报成红，除非确实不匹配）。
3. **`#L<n>` 行号锚点完全不校验**：它对代码文件有意义，但**行号会随代码漂移**，本闸门管不到 —— 这是有意的：行号锚点天然易腐，不该由文档闸门背。
4. **`~` 开头的链接目标不校验**：`~/foo` 不是仓内路径；若作者用 `~/` 指仓内文件，闸门会**放过**（与 §5.4 允许 `~/.codex` 这类家目录相对写法同源）。
5. **脱敏闸门仍不扫源码**：`scripts/*.cjs` 与 `src/**/*.test.ts` 里的字面路径仍未处理（round-159 §六.6 同源边界；它们是**默认值 / 夹具**）。
6. **闸门只管「路径骨架」**：主机名、**内网 / Tailscale IP**（某 `tests/` 文档里就有 Tailscale 地址）、端口号等**不在**本闸门范围（§5.4 只管路径；真实线程 id / 提交哈希本就允许保留）。
7. **「平台默认用户名」仍会命中**：本轮把命中处改成了占位符，但**类本身不会**因为用户名是 Ubuntu 云镜像默认账号 / `ec2-user` / `azureuser` 之类而放行 —— 它们仍是真实用户目录名。若某文档确实要拿它当示例，应**登记例外**而不是放宽类。
8. **链接闸门只校验「存在 + 锚点命中」**：**不校验**文档间语义一致性（如链接指向一个刚刚改名的标题的近似名）；站点绝对路径与带 scheme 的目标不校验。
9. **`.agents/` 是仓内被跟踪的 skill 文档目录**（另有 `.trae/`、`.zcode/` 等**已忽略**的第三方工具目录，round-159 已处理）⇒ 前者的文档也在脱敏范围内，本轮据此改了 1 处。
10. **本轮只收 round-159 §六 的 ⑦⑧ 两条 + §六.10 的复核**：§六 其余边界（①②③④⑤⑥⑨）与本节新记的 1~9 仍开放 —— 其中「脱敏闸门不扫源码」（5）、「`#L<n>` 不校验」（3）是**有意不做**，其余是**尚未做**。
