# 交接文档写作规范

> 本文档规定 `codex-mobile-handover/` 目录下交接文档的组织结构与写法约定，供后续会话遵循。交接文档的目标是让**下一个会话只读文档就能接续工作**：知道当前环境状态、最近改了什么、为什么改、还剩什么、怎么启动验证。
>
> 适用范围：本仓库（`codexapp` / codex-mobile）。其他仓库如无专门说明，可参考本文档的组织思路。

## 1. 目录结构与职责

```
codex-mobile-handover/
├── codex-mobile-handover.md   # 交接总入口（快照 + 索引 + 常驻信息）
├── rounds/                    # 按轮次验收/反馈的逐轮记录
│   └── round-NN-<主题>.md
└── sections/                  # 跨轮次的公共主题
    └── <主题>.md
```

| 位置 | 放什么 | 不放什么 |
|---|---|---|
| `codex-mobile-handover.md` | 当前快照、启动方式、未完成事项、注意事项、文档索引 | 单轮需求细节、根因分析、验证过程 |
| `rounds/round-NN-*.md` | 某一轮验收/反馈的完整记录（现象→根因→修复→验证） | 环境配置、跨轮方案 |
| `sections/*.md` | 环境、提交历史、跨平台回归、长期方案等公共主题 | 单轮事件流水账 |

**总原则：** 每个轮次新增一个 `rounds/` 文件，不往已有 round 文件里追加新轮内容；公共主题新增 `sections/` 文件。总入口永远是查看文档的第一站。

## 2. 总入口 `codex-mobile-handover.md`

### 2.1 当前快照（文件开头表格）

固定表格，每轮交接时更新，字段保持稳定以便对比：

| 项 | 说明 |
|---|---|
| Git 分支 | 当前分支 + 是否已同步 |
| Dev 端口 | 开发端口（本仓库固定 `4173`） |
| Dev 状态 | 运行中 / 未运行，HTTP 状态 |
| App-server | 是否正常响应 RPC |
| 工具链 | pnpm / Node / codex-cli 版本与安装方式（含跨平台差异） |
| 最近提交 | 最近一次提交哈希 + 一句话说明（含「本轮改动待提交」标记） |

### 2.2 文档结构（索引）

- 用「环境与主题」「按轮次记录」两个表格罗列 `sections/` 与 `rounds/` 文件，每行给出链接和一句话主题描述。
- 新增文件必须同步在本节登记；删除/合并文件必须同步删除链接。
- 文件命名与链接保持相对路径。

### 2.3 常驻章节

- **项目概况**：技术栈、入口、关键模块路径（一处维护，不做重复说明）。
- **启动方式**：普通电脑 / 沙箱内 / 跨平台（macOS 等）分别说明，含 PATH、环境变量、端口冲突规避。
- **未完成事项**：尚未推送的提交、未跟踪文件、依赖安装历史、跨平台回归状态、测试遗留。
- **交接注意事项**：脱敏占位、禁止重建被删的本地产物、端口与进程约束、git 提交惯例。

### 2.4 落款

文件末尾保留一行 `*codexapp · 交接文档 · <日期>（<最近进展一句话>）· 内容已脱敏*`，日期与进展随更新同步修改。

## 3. 轮次记录 `rounds/round-NN-*.md`

### 3.1 命名

- 前缀：`round-NN-`（两位数，如 `round-05-`、`round-30-`）。
- 后缀：英文短主题，连字符分隔，如 `round-30-feedback.md`、`round-25-zen-reasoning-fix.md`。
- 主题用「哪类内容」命名：`feedback`（反馈）、`fixes`（修复）、`handover`（交接需求）、`backlog`（待办）、`refactor`（重构）、`upstream`（上游移植）、`style`（样式）等，按实际内容选择，保持同类一致。

### 3.2 标题

```markdown
# Round-NN：<中文主题>（YYYY-MM-DD）
```

日期为当轮完成日期；主题一句话概括本轮内容。

### 3.3 开头背景

```markdown
> **背景：** <本轮反馈来源：哪条线程 / 哪个 provider / 什么现象，为什么做>
```

背景用于下一会话判断「这轮针对谁、解决什么」，必写。

### 3.4 每条需求/问题的结构

每条按以下顺序，缺一不可：

1. **现象/需求**（小标题或加粗）：用户原话或复述，可附截图/链接。
2. **根因**（`**根因（实测确认 / 代码确认）：**`）：必须给出依据——实测数据、真实线程 jsonl、代码路径分析，禁止猜测。
3. **修复**（`**修复（<涉及文件>）：**`）：改动点、涉及文件、为什么这样改；有设计取舍时说明备选。
4. **验证**：单测/构建/Playwright 结果，异常基线要标注（如既有环境性失败与本轮无关）。
5. 若是**调研结论**而非修复，明确写「**调研结论：**」，并给出结论依据与是否留待后续。

### 3.5 收尾验证说明

列表汇总本轮验证口径：

- `vue-tsc --noEmit` 是否通过；
- `pnpm run build:frontend` / 完整构建是否通过；
- 全量单测通过数 + 失败数，失败需注明是否既有环境性失败（给出具体用例）；
- Playwright 断言数与截图路径；
- 涉及文件清单（含新增文件）。

## 4. 公共主题 `sections/*.md`

- 每个主题一个文件，命名 `小写-连字符.md`（如 `auto-compact-plan.md`）。
- 文档内自包含：背景、方案/现状、结论、实施记录、评估。
- 跨轮次的进展在文件内「实施记录」节追加，不新建重复文件。
- 长期方案类（如 `reasonix-plan.md`、`parity-plan.md`）保留待办/完成状态标记。

## 5. 配套要求（联动规则）

1. **手动测试文档联动**：轮次涉及功能变更时，在 `tests/<domain>/` 新增/更新对应手动测试文档（命名 `round-NN-<主题>.md`），并在 `tests.md` 根索引与 `tests/<domain>/index.md` 登记。`tests.md` 只做根索引。
2. **git 提交惯例**：每个离散任务单独提交，提交信息具体、描述变更，不混提无关改动；代码修复与交接文档更新可同提交或分提交（推荐分开，历史更清晰）。
3. **推送**：直连 GitHub 失败时经本机代理 `git -c http.proxy=socks5h://127.0.0.1:10808 -c https.proxy=socks5h://127.0.0.1:10808 push`，不改全局 git 配置。
4. **脱敏与不写死路径**：用户名、本机绝对路径用 `<用户名>`、`<项目目录>` 占位；**工具链（node/pnpm/git/codex-cli 等）位置一律用语义占位**（`<node 安装目录>`、`<pnpm 全局 bin 目录>` 等），禁止出现任何具体路径骨架（含脱敏后的 `C:\Users\<用户名>\...` 结构）——本项目跨机器/跨平台运行，换机后路径必然不同；需要给出定位方法时写探测命令（`Get-Command`、`pnpm bin`、`npm prefix -g`），不写路径值。真实线程 id / 提交哈希可保留（便于复现）。
5. **可复现性**：根因结论尽量给出复现路径（线程 jsonl 路径、构造数据、临时测试），下一会话可自行验证。

- [ ] 验证口径齐全（vue-tsc / build / 单测 / Playwright）
